# Fork notes: Hummingbot client changes for Gateway on Ergo

This branch (`feat/ergo`) is Hummingbot v2.18.0 (upstream commit `3351adad0`) plus the commits on this branch. The first two (`89ab848da`, `669886ac1`) change how the client's Gateway connector waits for, tracks and books swaps; a later one gives the LP executor an AMM mode (section 2.1). The fork exists to be used with the Gateway fork that adds an Ergo chain (`feat/ergo` of the Gateway repository; see its `FORK-NOTES.md`).

This file is for someone who wants to run the client with that Gateway, or merge a new upstream release into this fork.

## 1. Why a stock client cannot track an Ergo swap

Two rules in the stock Gateway connector (`hummingbot/connector/gateway/gateway_base.py`) assume fast blocks and transactions that expire.

- **A fixed 120-second wait.** `SIGNATURE_POLL_TIMEOUT` and `TX_NOT_FOUND_DEADLINE` are both 120 seconds. The comments in the file tie them to Solana's blockhash window of about 90 seconds. Ergo blocks average 120 seconds (`blockTimeSeconds` in the Ergo network config). A swap can be mined after the client has stopped waiting.
- **Re-submission after "not found".** If a transaction is still NOT_FOUND when the wait ends, the stock client treats it as dropped and submits the swap again, and counts NOT_FOUND toward the order tracker's lost-order limit. That is safe only where an unseen transaction can never land later. An Ergo transaction has no expiry. One the node has lost may still be mined, so a second submission could trade twice.

The commits change both rules, add `ergo` to the client's chain list, send a price limit with swaps on connectors that enforce one, and book a fill from the amounts Gateway says the transaction fixes.

## 2. What the two commits change

`89ab848da`: track swaps to a final state on slow-block chains and bind their price.
`669886ac1`: book a swap from the amounts its transaction fixes, and read what Gateway states.

- **Chain list.** `ergo` is added to the `Chain` enum. A new function `known_chains()` returns those names followed by any other chain the running Gateway reports in `/config/chains`. The AMM data feed, Gateway pricing in the market data provider, market start-up and `gateway balance` with no chain named use it.
- **Waits from the network config.** If a network's Gateway config has `blockTimeSeconds` (and optionally `confirmations`), the swap's own poll and the NOT_FOUND deadline wait the longer of 120 seconds and `blockTimeSeconds x (confirmations + 5)`, capped at 3600 seconds. With the shipped Ergo mainnet config (120 s, 1 confirmation) that is 720 seconds. A network config that cannot be read at start is read again on status polls and new swaps, at most every 30 seconds.
- **No re-submission where "not found" proves nothing.** NOT_FOUND counts as proof of a dropped transaction only if the network config has been read, names no `blockTimeSeconds`, and does not say `transactionsExpire: false`. Otherwise the swap is never re-submitted, its hash is saved with the order as soon as Gateway names it, the order stays open, NOT_FOUND never counts toward the lost-order limit, and one warning is raised for an order still not found after the deadline. Such an order ends only on CONFIRMED or FAILED. If the reply to the submit call is lost on such a network, the order fails with the marker `SUBMIT_OUTCOME_UNKNOWN`; the order executor then does not place it again and the LP executor holds the withdrawn tokens.
- **Price limit.** An AMM swap on a connector that enforces one is sent `minAmountOut` (SELL) or `maxAmountIn` (BUY), computed from the order price and slippage, rounded to 15 significant digits and then to the quote token's decimals in the tightening direction (up for a SELL's minimum, down for a BUY's maximum). The order fails before anything is sent if the decimals are unknown or the limit cannot be written as a JSON number. A connector is in the set if it is `ergodex` (built in) or if Gateway states `binds_price_limit: true` for it in `/config/connectors`. A stated `false` never removes `ergodex`. No other connector is sent a limit.
- **Booking from `pendingData`.** If Gateway answers a swap PENDING with `pendingData`, the client keeps those amounts, with the transaction's signature, on the open order (saved with the order, so it survives a client restart). Nothing is booked from them until poll reports that same transaction confirmed. Then the fill is booked from those amounts and fee. A Gateway that sends none is handled as before.
- **Orders with no usable price.** The client asks Gateway for a quote alongside the submission and books a confirmed fill at that quote, or at price 0 with an error logged if none arrived. It used to book NaN.
- **Other.** `cancel()` on a Gateway swap order logs a warning and returns; the order stays open. A swap still unresolved when its own poll ends keeps the order open on its hash. `transactionsExpire: false` forbids re-submission and never allows one the older rule would not. The re-submission rule is read once per swap, before its first submit.

## 2.1 The LP executor on AMM pools

Upstream's LP executor manages concentrated-liquidity (CLMM) positions only. This fork adds an AMM mode, chosen when the executor's `lp_provider` has trading type `amm` (for example `ergodex/amm`). CLMM behaviour is unchanged.

- **A position** is the LP tokens one deposit acquired, in one pool. There is no price range; a config that sets `lower_price` or `upper_price` in AMM mode is refused. Fees accrue inside the pool's reserves, so there is nothing to collect; the fee fields are zero and volume is derived from the growth of the position as for CLMM.
- **Open and close.** Open is one Gateway AMM add. With a Gateway that states what a liquidity transaction moves (`pendingData` on a pending answer, or `data` when confirmed), the position's LP is exact and its close removes exactly that LP (`lpTokenAmount`). With a Gateway that does not, amounts are estimated from readings of the wallet's holding before and after, the close is by percentage, the estimates are labelled in the executor's info, and another movement of the same pool's LP in the wallet can be counted as this position's.
- **Exits.** `upper_limit_price` and `lower_limit_price` close the position once the price has stayed past the limit for at least one block time (the chain's `blockTimeSeconds`, or `position_refresh_interval` where it is unknown). A deposit is refused when the price is already past a limit.
- **One executor per pool.** In one client process, one AMM executor per chain, network, wallet and pool (the pool id in any case); a second refuses to start and says why. The claim is given up only on a clean end. It stays held while a transaction of the executor may still land or its LP is still in the pool (an unknown or unmeasured deposit, a forced stop, a withdrawal of unknown outcome, a pool that cannot pay in full, a percentage close that left a residue). Release it by hand with `LPExecutor.release_amm_pool_claim(chain, network, wallet_address, pool_address)` after checking the wallet on chain. Actions outside this process on the same wallet are not covered.
- **Never twice, never orphaned.** A deposit is not sent after an early stop, not sent again when its outcome is unknown, and not booked from the offer. An unknown deposit is followed for `blockTimeSeconds x (confirmations + 10)` (22 minutes on Ergo mainnet), polled by its transaction id, and booked exactly once it confirms; without a verdict it ends in a hold. The unclosed-position marker in the executor's stored info carries the pool, the LP amount (or the reading before the deposit), and the transaction hashes, also on a forced stop.
- **The LP rebalancer** controller stays CLMM-only and refuses an AMM provider.

## 2.2 Arbitrage and XEMM after a swap of unknown outcome

A swap that failed with `SUBMIT_OUTCOME_UNKNOWN` may still land, and Gateway has no duplicate guard, so placing it again can trade twice. The connector keeps the reason (`order_failure_reason`); these strategies now read it.

- **Classic `amm_arb`.** After a leg fails with the marker, no new proposal starts, including the rest of the proposals found in the same round. Non-concurrent mode still drops the proposal before its second leg; a CEX leg already placed (concurrent mode) is left to run as before. The hold ends when the connector reports that order filled, or when the hold window has passed and a balance refresh after it has succeeded. The window is `blockTimeSeconds x (confirmations + 10)` as the connector read it from Gateway (22 minutes on Ergo mainnet, the LP executor's window), 30 minutes when the block time is unknown. A later failure report for a held order changes nothing. After a fill, too, the held market's balances are refreshed first. A failed refresh is tried again at most every 10 seconds. The hold's end rests on Gateway's balance counting its own mempool transactions: it is a time-plus-balance heuristic, not a verdict on the swap. The hold-start warning names the order and the hold end, and says whether the other leg was sent (then that leg is unhedged if the swap does not land) or not placed (then the position is one-sided if the swap lands). The status shows the hold under warnings. At the hold end a warning, also sent to the app, says whether the held market's base balance moved by at least half the order amount in the order's direction since the balance read right before the order was placed (a read at failure time may already include the swap): if it did, the swap appears to have landed; it also says when the balance had already moved before the failure was reported. The hold lives in the process: a strategy `stop`/`start` keeps it, for the same connector name and, when both are known, the same wallet address; a process restart forgets it.
- **v2 `ArbitrageExecutor` and `XEMMExecutor`.** A failed order with the marker is not placed again, and once it has failed neither leg is placed again. The executor keeps the failed order's id, logs an error naming it and the other leg's state, and keeps listening until the other leg is done (filled, failed or cancelled); it stops at once if the other leg was never placed. It then ends with close type `FAILED` (`POSITION_HOLD` is not used: the position store needs a `connector_name` these configs do not have). Its custom info carries `outcome_unknown_order_id`, `outcome_unknown_connector`, `outcome_unknown_close_timestamp`, `outcome_unknown_waiting_since` (when the order was flagged), and the other leg's id and executed base amount. When the other leg of an `ArbitrageExecutor` also fails with the marker, it logs that both swaps may land and adds `outcome_unknown_other_connector`; the controller then holds and refreshes both connectors. If the other leg is still not done once the hold window has passed since the flag, the executor logs an error at most every 600 seconds naming that leg, its state and executed base; it is not stopped, and the controller stays held until the executor is stopped by hand after the chain is checked. A filled other leg is not unwound. Any other failure is re-placed as before.
- **v2 controllers `arbitrage_controller`, `xemm_multiple_levels` and `ergo_pool_arb`.** Once an executor of such a controller carries `outcome_unknown_order_id`, every `arbitrage_controller`, `xemm_multiple_levels` and `ergo_pool_arb` in the process that uses that connector creates no new executor (an `ergo_pool_arb` still sells a buy that has filled, section 2.3) in either direction or at any level: while that executor runs, for the same window after its close timestamp, and then until a balance refresh of that connector has succeeded (retried at most every 10 seconds). The hold lives in the process, not in the controller: it survives the closed-executor buffer trim and a strategy `stop`/`start` (an executor that disappears before it was seen closed counts as closed when its controller, by id, notices it gone), and a process restart forgets it. Executors already running keep trading; only new executors are held. Other controllers and scripts that use these executors are not held.

## 2.3 A pool per swap, and the Ergo pool arbitrage controller

Upstream's client never names a pool on a swap or a quote, so Gateway picks the best pool per direction and size, and a BUY and a SELL on one pair can be priced on two pools. A caller can now name one.

- **Pool per order.** `GatewayHttpClient.quote_swap` and `execute_swap` take an optional `pool_address`, sent as `poolAddress` on the AMM and CLMM routes; named on the router route it is refused before anything is sent. `Gateway.get_quote_price` and `buy`/`sell`/`place_order` (kwarg `pool_address`) pass it on. The pool is kept on the open order (`GatewayInFlightOrder.pool_address`, saved with the order), so the quote taken for an order placed without a usable price, and a second submit of the same order, use that pool. With no pool named, every request is the one sent before: no field is added.
- **The pool a quote came from.** `Gateway.get_quote_price_and_pool` returns the price and the `poolAddress` of Gateway's answer (None when the answer names none). When a pool was named and the answer names another, the price is None and an error is logged. When a pool was named, the answer's `tokenIn` and `tokenOut` must also be the pair's tokens in the side's direction (a BUY pays the quote token for the base token), looked up in the token list (on Ergo the native coin is the all-zero id); an answer naming no tokens, or other ones, gives no price and an error. A named-pool quote on an EVM chain of a pair with the native coin (ETH, where the token list carries only WETH) therefore gets no price, since only Ergo's native coin is mapped; no existing caller names a pool there. `Gateway.get_quote_price_and_pool_fresh` is the same quote without the 5-second cache. Every swap logs the pool it was placed on (or that Gateway chooses). The pool in a confirmed answer is the pool the route was given, stamped by Gateway, and is logged; ergodex answers every swap PENDING, so `_log_swap_pool` logs nothing for an Ergo swap. Gateway enforces the pin there: it builds the swap on the named pool's box.
- **Order executor.** `OrderExecutorConfig` takes `pool_address` (passed to the Gateway connector only when set; on a non-Gateway connector the order is not placed and the executor ends `FAILED`) and `max_retries` (None keeps the executor's own budget; when set, the executor stops at once when the budget is spent instead of placing once more). A failure with `SUBMIT_OUTCOME_UNKNOWN` now also puts `outcome_unknown_order_id`, `outcome_unknown_connector` and `outcome_unknown_close_timestamp` in the executor's custom info, which `ControllerOutcomeHold` reads.
- **Controller `controllers/generic/ergo_pool_arb.py` (new).** One connector (`ergo-mainnet`), one pair, two pool ids (`pool_a`, `pool_b`, 64 hex, different). The config is refused when `min_profitability` (a fraction) is not above twice `slippage_pct` (a percent) / 100. Before trading, each pool is read once by pool-info and must hold the pair's two tokens (by address from the token list, in either order); a pool of another pair, or a `slippage_pct` that at `order_amount` is less than one unit of the quote token, in which the price limit of both sides is written (decimals from the token list), makes the controller log an error and create no executor. When nothing is in flight it quotes a BUY on one pool and a SELL on the other for `order_amount`, both directions, each quote pinned and checked to come from the pool named. When the net edge, `(sell - buy) x amount - 2 x network_transaction_fee`, over the buy cost is above `min_profitability`, it buys on the cheap pool (an `OrderExecutor`, LIMIT at the buy quote, `slippage_pct` bound into the price limit, no retry), and only after that buy is filled re-quotes the other pool and sells the bought amount there, pinned, at that fresh quote. One arbitrage at a time, then `delay_between_arbitrages`. The network fee is in the chain's coin; it is priced in quote from the pair when the pair holds the coin, else from `fee_token_price_quote`, else nothing is traded. `order_amount` has no default and must be set: on ERG-SigUSD (SigUSD has 2 decimals) 0.5 % of 1 ERG is under 0.01 SigUSD while ERG is under 2 SigUSD, so a small size is refused; for example `order_amount: 10` with `slippage_pct: 0.5` binds a tolerance of about 0.05 SigUSD at 1 SigUSD per ERG.
  - A buy that failed definitely: nothing was bought; the arbitrage is dropped and quoting resumes after the delay.
  - A buy of unknown outcome: no sell; an error says the amount may be held unhedged; the controller is held (section 2.2 window and balance refresh), then resumes.
  - A sell that failed definitely with nothing booked is re-quoted one block later (the connector's `blockTimeSeconds`, 120 seconds when unknown), uncached (`get_quote_price_and_pool_fresh`), and placed again at that quote, up to `sell_attempts` (default 3) in all, so the attempts are spaced at least a block apart. Every sell quote, the first at the buy's fill too, must give at least the buy cost less `max_sell_loss_pct` (default 1, a percent). A quote under that floor is not acted on at once (it may price a box not yet confirmed): the pool is quoted again one block later, and the controller halts only if that quote is still under the floor; otherwise it sells. Once the attempts are used the controller halts.
  - `max_sell_loss_pct` bounds the sell quote against the buy cost (buy quote x bought amount), not the realised loss. The sell may fill up to `slippage_pct` under its quote, the buy may have filled up to `slippage_pct` over its quote, and both network fees are left out, so the realised loss can reach about `max_sell_loss_pct` + 2 x `slippage_pct` plus both network fees (2 % plus fees at the defaults).
  - A sell of unknown outcome, or whose executor vanished or never started, is not placed again: the controller halts. A sell that failed but booked any fill halts it too, without a retry (a retry would sell the full amount again), and lists the buy. A buy that completed with no base booked halts it too.
  - A halt stops the controller creating executors and logs an error naming the bought amount, pool, price and executor that are not sold. The halt lives in the process, by controller id, connector, pools and pair (the pair in any case): a strategy `stop`/`start` or a rebuilt controller of the same config stays halted. Another controller config of the same pools and pair is not halted by it and still sells its own filled buy. A process restart clears it; check the wallet first.
  - Possibly unhedged buys (a buy of unknown outcome, and the buy of every halt) are listed, with order id, amount, pool, price and reason, in the status and the custom info (`possibly_unhedged`), kept in the process as the halt is, until a new process.
  - A hold from another controller on the same connector does not hold the sell of a filled buy: the hold stops new exposure and the sell reduces it. A warning is logged and the sell pool is re-quoted. New buys stay held.
  - The controller's state lives in the process. A restart while a leg is open forgets the arbitrage (the executors are not resumed).

## 2.4 The NonKYC exchange connector

`hummingbot/connector/exchange/nonkyc/` is a spot connector for NonKYC (`https://api.nonkyc.io/api/v2`, websocket `wss://api.nonkyc.io`). It is the exchange leg against the Ergo pools, for example `amm_arb` on ERG/USDT. Hummingbot finds it by its folder name, like every other exchange connector. Nothing outside the folder was changed to register it.

**Source and licence.** The code is ported from `NonKYCExchange/hummingbot`, folder `hummingbot/connector/exchange/nonkyc/`, at commit `4d9a98e1e` (2026-02-20), written for Hummingbot 2.12. That code is under the Apache License 2.0, the same licence as Hummingbot. The package docstring in `__init__.py` credits it. `dummy.pyx` and `dummy.pxd` are kept for the Cython build.

**What was changed, and why.** Two reviews of the source (`REVIEW-nonkyc-adversarial.md`, `REVIEW-nonkyc-money-path.md`) found faults that could book fills twice, lose fills, mark live orders failed, and send orders with no price. The port fixes them:

- **Orders.** Only LIMIT orders are offered. MARKET is not, because on a thin book it fills at any price and the connector dropped the price; NonKYC documents no post-only flag, so LIMIT_MAKER is not offered either. The order type is sent as `limit` (lower case, as the spec says), the price is always sent, and `strictValidate` is on so NonKYC refuses rather than truncates.
- **Local checks before sending.** Minimum order value (`minQuote` when `isMinQuoteActive`, 1 USDT on ERG/USDT) and minimum size (`minimumQuantity`) are read from `/market/getlist`, never hard-coded, as exact decimals. `isPaused`, `pauseBuys`, `pauseSells`, `apiExcluded` and the allowed price range are checked before each order. A failing order fails locally and nothing is sent. Size and price are rounded down to the market's steps by the base class. The market list (and so the pause flags) is re-read every 60 s, not every 30 min. The same check is public as `check_order_locally(trading_pair, is_buy, amount, price) -> Optional[str]` (the reason NonKYC would refuse, or None; nothing is sent), so a strategy can ask before it trades elsewhere.
- **One fill path.** A fill is booked only from a NonKYC trade record (`/account/trades`), keyed by the trade's own `id`. Order records and websocket reports are never booked: their `executedQuantity` is cumulative and only tells the connector that trades are missing. A trade that would fill an order past its amount is refused and logged. Fills from the REST poller, the per-order fetch and the websocket path all go through the same function, so a trade seen twice is booked once, also after a restart (saved fills carry their trade ids).
- **Order requests with an unknown outcome.** A createorder that times out (10 s), returns 5xx or 504, returns error 20008 (duplicate client id) or returns a reply without an order id does not fail the order. It stays pending for a grace period of 300 s. In that time each status poll looks it up by `userProvidedId` in getorder and, when getorder does not find it, in `/account/orders`: asked without `status`, then with `status=filled`, then with `status=cancelled` (the spec gives `status` no default, so the default may list active orders only), stopping once it is found; records are merged by id. A full page (500) of `/account/orders` is a network warning the operator sees, because an older order in the window is then not read. "Not found" answers in that time do not count toward "lost", and neither do they while the createorder request is still in flight, nor when a cancel of the pending order looks it up. Found: the order gets its exchange id, its state and its fills. Still not found after 300 s: the order fails with a reason containing `[code: SUBMIT_OUTCOME_UNKNOWN]`, readable through `order_failure_reason(order_id)`, so `amm_arb`'s outcome hold (section 2.2, 1800 s on NonKYC, which has no block time) starts instead of a new proposal. Its client id then stays on a sweep list for 24 h: every 60 to 120 s (the sweep runs in the status poll, which is 120 s apart when no order can fill and the websocket is up) `/account/orders` is read the same three ways, and a listed order that appears is cancelled if open and its fills are booked under its client id. The order is never sent twice. Only a clear refusal (for example 20001 insufficient funds, 10001 validation, 401, 429) fails the order at once.
- **Status polls.** getorder uses NonKYC's order id once known, the client id before. Only NonKYC's 20002 answer counts toward "lost". 429, 5xx, timeouts, bad bodies and unknown statuses are logged and retried, and any real answer resets the count. Because 20002 also covers a filled order, an order with an exchange id has its trades read before a 20002 is counted: filled in full, it completes; trades unreadable, the 20002 is not counted. Lost orders have their fills read before the lost-order cancel, and a lost order filled in full is not cancelled. An inactive "Partly Filled" order is treated as cancelled. A terminal status whose trades have not arrived is held back for up to six deferrals while the trades are fetched; at most one deferral counts per order per 5 s, so a burst of websocket reports cannot use them up. A pending order found already finished (no created event fires) has its exchange id recorded, so later fills of it can still be booked.
- **Cancel** sends NonKYC's order id, learnt by client id first if the create reply was lost. A cancel without `success: true` is an error, not a cancel. A cancel that times out is not counted as "not found" (the base class counts it). Fills made before the cancel are fetched before the order is marked cancelled. The trade list can lag the cancel: after `success: true` the order is re-read by NonKYC's id, and if its record shows more executed than the trades booked, the order is not marked cancelled; the status poll applies CANCELED or FILLED once the trades are listed (or after the six deferrals).
- **Signing.** The signature is over the exact bytes sent: the GET query is built once and put in the URL, and the POST body is compact JSON, set as the body and signed as is (the old code signed one string and sent another). The nonce is in milliseconds, as the spec says, and never repeats or goes back. Signed requests go out one at a time, from signing to reply, so a later nonce never reaches NonKYC first. The cost: a slow signed request (up to the 30 s request timeout, 10 s for createorder) delays the next one, including a createorder. The websocket login nonce comes from `secrets`.
- **Fees.** Default 0.2% maker and taker (NonKYC's base tier). The spec says a trade's `fee` is in the quote asset, NonKYC's FAQ says the asset received, so the asset is read per trade: on a buy, `totalWithFee` equal to quantity x price + fee (within 1e-8) books the fee in quote, added to the cost; equal to quantity x price books it in base, deducted from what was received. When neither (or both) match, the quote default is kept (`buy_percent_fee_deducted_from_returns=False` for estimates) and this is logged once. Sells book the fee in quote (spec and FAQ agree). A fee paid in another asset (`alternateFee > 0`, `alternateFeeAsset`) is booked alone, in that asset, never together with `fee`.
- **Order book.** Websocket snapshots and diffs are ordered by the websocket book `sequence` (before, the snapshot used seconds and the diffs milliseconds, so stale diffs were replayed). The REST `/market/orderbook` `sequence` is the trade counter, not the book sequence (live check, finding A), so it is never used as a book id: a REST snapshot (start-up, or the hourly refresh when no websocket is up) gets id 0, replays no saved diff, takes no diff, and is replaced by the next websocket snapshot. The websocket `snapshotOrderbook` is used as a snapshot. Diffs are sequenced as they are read: the next sequence, or the same one again, is applied; a diff up to 3 sequences ahead is held for up to 1 s for the missing ones and then applied in order (NonKYC sometimes sends two adjacent diffs swapped, finding B); a larger gap, a missing diff that does not come in time, a backward sequence, or a diff before any snapshot on a new connection logs a warning and resubscribes the pair, at most once per 30 s per pair; a resubscribe wanted sooner is queued, not dropped, and a snapshot that arrives first cancels it. A pair with no websocket book message for 60 s is resubscribed (quiet ERG books are, about once a minute). A pair added while running is resubscribed 5 s later, because the tracker drops the snapshot that comes before its book exists. A diff without a sequence is not applied and makes the connector not ready (`status_dict["order_book_sequenced"]`) for 60 s. On a websocket snapshot only the run of saved diffs that follows it without a gap is replayed. The hourly refresh resubscribes rather than mixing in a REST snapshot. Snapshot and subscription depth are both 100. Each trade of a batched public trade message is kept.
- **Base-class bug worked around.** `OrderBookMessage.__lt__` in the core ends with `or self.has_update_id`, so `OrderBook.restore_from_snapshot_and_diffs` replays every saved diff whatever its id, for every connector. The core is not changed; `NonkycOrderBook` overrides the restore (a test shows the stock restore brings a stale level back after a sequence reset) and ignores diffs older than its snapshot.
  - For upstream (not sent): `hummingbot/core/data_type/order_book_message.py:88-96`, the final clause of `__lt__` is `(ts != other.ts and ts < other.ts) or self.has_update_id`, so any snapshot or diff is "less than" anything, and `bisect_right(diffs, snapshot)` in `OrderBook.restore_from_snapshot_and_diffs` always returns 0: every saved diff is replayed. Impact on other connectors is narrow (reviewer's reading): diffs carry absolute levels and the 32-diff window is the newest contiguous run, so replaying it usually ends at the right values. Corruption needs a snapshot newer than every diff in the window (for example a REST snapshot while the websocket lags); the replay then sets levels back to older values, the tracker's router (`order_book_tracker.py:556`) rejects the diffs in between that would have corrected them, and the stale levels last until that price changes again. A fix (for example `... or (self.timestamp == other.timestamp and self.has_update_id and other.has_trade_id)`) changes sort order wherever `OrderBookMessage` is compared, so it needs its own tests upstream.
- **Websocket user stream.** The login reply is awaited and checked before subscribing; a refused or unanswered login reconnects after a backoff of 5 s, doubling up to 300 s, reset by a good login. Only `subscribeReports` is sent (`subscribeBalances` is undocumented). A report only makes the connector re-read that order and its trades over REST, so unverified report fields are never trusted. Balances come from REST only. The status poll runs every 5 s while any order can still change, because websocket pings keep the stream looking alive even when no report arrives.
- **Rate limits.** NonKYC publishes none. The limits are low on purpose: 10 public requests per second, and two separate private pools of 5 per second, one for createorder and cancelorder and one for getorder, trades and balances, so polling never spends the order budget. A 429 pauses requests for 10 s. `/account/orders` (the unknown-outcome lookup and sweep) is in the query pool.
- **Other.** Server time from the documented `GET /time`; a failed time sync is a warning. One bad trade reply no longer stops balance and status updates. The trade cursor moves only after a good reply, and only to trade times NonKYC gave, with a 60 s overlap. The spec caps `/account/trades` paging at skip 500 with no `until`, so at most the newest 1000 trades of a window are read; hitting that cap is a network warning the operator sees, and older trades in that window are not read. No `print`. Key and secret are held by the exchange object (to build the auth object) and by the auth object; they are never logged or put in a URL.

**Operator notes.**

- Make a fresh NonKYC API key for this connector: trading only, no withdrawal, IP-locked if offered. Do not reuse a key that was used with the old connector: its nonces were ten times larger, and if NonKYC keeps the highest nonce per key, millisecond nonces would be refused.
- Set the account's real fee tier in `conf/conf_fee_overrides.yml` (`nonkyc_maker_percent_fee`, `nonkyc_taker_percent_fee`) if it is not 0.2%.
- With `amm_arb` (`concurrent_orders_submission: false`), the NonKYC leg is a LIMIT order at the buffered price. Before the Gateway leg is sent, `amm_arb` now runs the NonKYC leg through `check_order_locally` at the buffered price and amount (a connector without it gets a generic check from its trading rules: minimum size, minimum notional, amount rounding to zero) and skips the proposal, with a log line, if it would be refused. NonKYC has no immediate-or-cancel flag, so the NonKYC leg is given `cex_leg_timeout` seconds (default 30, in the strategy config), counted from when the connector says the createorder request went out (`create_request_sent`; after the wait for the signed-request lock and any 429 pause, before the throttler's own wait of about a second at most; at most `cex_leg_timeout` is spent waiting for that), and then cancelled. After the cancel it waits `cex_leg_timeout` again plus 30 s (6 deferrals x 5 s, the time the connector may hold back a cancelled order's state while its trades are listed). If the NonKYC leg then fails definitely, is cancelled (also by hand: `amm_arb` now handles cancel events, so it no longer hangs), or does not fill in full after the Gateway leg traded, `amm_arb` logs an ERROR, notifies with the unhedged amount (booked so far vs asked), and starts no new proposal until the strategy is restarted. A fill of that leg booked after the halt logs another ERROR and notifies the corrected booked and unhedged amounts. A NonKYC leg whose create outcome is unknown halts too, it does not just hold: with the defaults the strategy halts at about 90 s after the request (30 s, the cancel is not sent while the order is looked up, then 60 s) saying the leg may still be open, and the connector fails the order with the marker at about 315 s, which starts the outcome hold (section 2.2) as well; with a longer `cex_leg_timeout` the marker failure lands inside the waits and halts at once. Either way the end of the hold does not resume trading: check the NonKYC order, then restart the strategy. Order size must clear 1 USDT at the buffered price (over 5.3 ERG at 0.1888).
- Not guarded: if NonKYC ever stopped sending a websocket snapshot on subscribe, a pair's book would stay at its REST snapshot (diffs are not applied to a book with id 0) while the connector reports ready; every subscribe in the live check brought one.
- Classic `amm_arb` checks connector readiness only until it first starts trading, so the "diff without sequence: not ready" guard stops it only at start-up; it bites on every tick only for strategies that check `ready` each tick.
- Not done (outside this fix round): `amm_arb`'s budget check for a NonKYC buy does not add the 0.2% fee (a buy that needs exactly the balance can still get 20001 after the Gateway leg; it now halts the strategy rather than looping); `tradingStartsAt` from the market list is not checked (not set on the ERG markets); orders restored after a restart while still pending do not get the 300 s grace (they are looked up by client id and counted as before), and the unknown-outcome sweep list is in memory, so a restart forgets it.

## 3. What stays identical for Solana and Ethereum, and what does not

Stay identical, when the client has read the network config: the 120-second waits and the re-submission rule. The stock Solana and Ethereum network templates in the Gateway fork carry neither `blockTimeSeconds` nor `confirmations` (checked in `src/templates/chains/solana/` and `ethereum/`). No price limit is sent to any connector other than `ergodex`, unless Gateway states `binds_price_limit: true` for it.

Change for every chain:

- A swap unresolved when its own poll ends keeps the order open on its hash instead of marking it failed. The status loop then resolves it.
- A timeout error that names its transaction is polled even when no retries remain. The LP close path can therefore wait up to the poll timeout.
- Order status results stay paired with their own order when some tracked orders have no hash yet.
- A failure raised after the status loop has already resolved the order is logged and ignored.
- A fill is never booked at NaN or a non-positive price; the quote fallback above applies to any order placed without a usable price.
- `cancel()` on a Gateway swap order no longer raises.
- Until a network config has been read, NOT_FOUND is taken to prove nothing, so an unreadable Solana or Ethereum config at start leads to no re-submission until it is read. Once it is read, the old rules apply.
- `known_chains()` always includes the enum members, so in `TradingCore` the Gateway chain test no longer falls back to a two-name set when Gateway has not reported. In the market data provider the Gateway-network test now matches `"<chain>-"` rather than a bare chain prefix. `gateway balance` with no chain named lists only chains Gateway has reported, once it has reported any.

## 5. What is proven and what is not

Proven:

- Unit tests, run in a container. At `669886ac1`, on the touched test files: 654 pass and 2 are skipped (615 and 2 after the first commit). `flake8` was clean after the first commit. These figures are from the commit messages.
- With section 2.3, on the Gateway, LP, order, arbitrage and XEMM test files and the controller tests: 954 pass and 2 are skipped in a container at commit `eee4b35a6` (872 and 2 before it); `flake8` clean on the changed files. The new named-pool tests fail on the prior sources, except one that checks only that `buy` forwards kwargs; those that check a request with no pool pass on both.
- A read-only run of the patched client library against the forked Gateway, on 25 November 2026. It used the first commit (`89ab848da`), not `669886ac1`. The client library read chains, connectors, network status, token lists, balances, pool info and quotes for `ergo`; built a Gateway connector object for `ergodex/amm`; read the network timing (120 s blocks, 1 confirmation, 720-second waits); and computed price limits. It sent no swap and no wallet request. The Gateway in that run was also an earlier commit than the current Gateway head.
- NonKYC (section 2.4): its tests and the `amm_arb` tests pass in the container, figures in the commit message. Against the original, unrepaired source, 53 of the port's first 62 tests failed. Each later fix round added tests that fail on the code before that round. A read-only live check of the public REST and websocket endpoints (no key) on 26 November 2026 matched the order book, trade and market-rule shapes the connector expects.

Not proven:

- No real swap has been tracked end to end. The status loop on a real transaction, the not-found handling over time, the lost-order limit and the restore of saved order state were not exercised against a live transaction.
- Strategies and executors other than through their unit tests, `TradingCore` start-up with trading on, and the application's own `gateway` commands were not exercised.
- Strategies other than the order, LP, arbitrage and XEMM executors and classic `amm_arb` do not read the `SUBMIT_OUTCOME_UNKNOWN` marker and may place a possibly submitted order again (section 2.2 covers the last three). Classic XEMM (`cross_exchange_market_making`) is not covered.
- Of the v2 controllers only `arbitrage_controller`, `xemm_multiple_levels` and `ergo_pool_arb` hold after an executor reports an unknown outcome; another controller or script using these executors may start a new one at once.
- `ergo_pool_arb` has run only in its unit tests. No LithosDex swap has been accepted by a node (Gateway FORK-NOTES), and LithosDex pools are found on chain and admitted by Gateway's rules when `networks.<network>.lithos.discoverPools` is true (the shipped mainnet value); with `discoverPools: false` a LithosDex pool must be on `lithos.poolAllowlist`. A non-empty `lithos.poolAllowlist` restricts LithosDex to the listed pools. Its profit test uses quotes taken minutes before the sell is mined; the sell is re-quoted when the buy fills, and its price limit is that quote less `slippage_pct`, so a pool that moves before the sell is mined fails the sell; after `sell_attempts` such failures a block apart, or a fresh quote still under the loss floor a block after the first, the controller stops with the buy unhedged.
- A process restart during a hold forgets it; check the chain before restarting.
- NonKYC: no request has been sent with a key. The private reply shapes come from NonKYC's OpenAPI spec (v1.3.0); the keyed checks in section 2.4 are still to be run, at tiny size, by the operator.
- A swap failed as possibly submitted has no hash. If it landed, its fill is not booked and the chain must be checked by hand.
- Where NOT_FOUND proves nothing, a transaction that was truly dropped leaves its order open.

Two behaviours seen in the read-only run that you should know about:

- A quote with only a pair named lets Gateway choose the pool, so a BUY and a SELL on the same pair can be priced on different pools. Stock strategies still name no pool; only a caller that passes `pool_address` (the order executor, `ergo_pool_arb`) pins one (section 2.3).
- On a token with few decimals, the price limit can equal the quote. For SigUSD (2 decimals), a 1 percent tolerance on 1 ERG rounded to no tolerance in the run. The rounding is deliberate: a pool pays whole units, and tests in the second commit pin it.

## 6. Merging a new upstream release

The changes are in the Gateway connector files and a few callers, so conflicts are most likely in `gateway_base.py` and `gateway.py`.

1. `git fetch upstream --tags`. Choose the release tag.
2. Merge it into a working branch made from `feat/ergo`: `git merge <tag>`. `feat/ergo` is published on the fork remote at the same head as the local branch, so use a merge, not a rebase, which would need a force push.
3. Resolve conflicts in the files in section 4. Keep upstream's change and re-apply the fork's: the block-timing reads, `proves_dropped` passed through `_execute_with_retry` and `_await_signature_terminal`, the `known_chains()` callers, and the price-limit code.
4. Search the merged tree for new uses of the `Chain` enum or of a hard-coded chain list (`grep -rn "Chain\b\|GATEWAY_CHAINS\|'ethereum'" hummingbot`) and route any new one through `known_chains()`.
5. Run what upstream's CI runs (`.github/workflows/workflow.yml`): `pre-commit run --files <changed files>`, then `make test` and `make report_coverage`, then `diff-cover --compare-branch=origin/master --fail-under=80 coverage.xml` on a pull request. The CI environment is the conda environment from `setup/environment.yml`.
6. Run the Gateway test files in section 4 on their own and compare with 654 passed and 2 skipped. A different count is expected if upstream changed those files.
7. Check that the Gateway fork you pair it with still answers `binds_price_limit` in `/config/connectors`, `pendingData` on a PENDING swap, and `transactionsExpire` in the Ergo network config. The client reads all three.
